## ⚠️ Responsible Use

Cellrift is a test tool for protocol-level scenario testing of telecommunications signalling systems. Running it generates real SIP and Diameter traffic — REGISTER, INVITE, UAR/CCR, and similar messages that a live network will process as genuine signalling.

**We strongly recommend running Cellrift only against environments assigned to test activities** — a lab, a staging deployment, or infrastructure you own or have explicit permission to test — **and not against production telecom networks.** Pointing a signalling test tool at production infrastructure can register bogus subscribers, open spurious call legs, or trip fraud and rate-limiting controls you don't want tripped.

This is a safety recommendation for how to use the tool well, not a legal condition of using it.

## Data Processing Agreement (DPA) Template

This section provides a template DPA for organisations that require documentation of data processing arrangements under GDPR or equivalent regulations.

**Parties**

- **Data Controller:** the organisation or individual operating Cellrift ("you", "the operator")
- **Data Processor:** not applicable — Cellrift is a locally executed open-source binary that processes no data on behalf of the operator and transmits no data to third parties

**Scope**

Cellrift runs entirely within the operator's own environment. The Cellrift binary, Docker image, and all associated tooling operate locally. No test inputs, test results, captured traces, protocol messages, or subscriber identifiers are transmitted to the Cellrift project, its maintainers, or any third-party service.

**Data Controller responsibilities**

The operator, as Data Controller, is responsible for:

- Ensuring that any subscriber identifiers, phone numbers, SIP URIs, or other personal data used in test scenarios are synthetic (fabricated) unless a legitimate lawful basis exists for using real data in a controlled test environment
- Ensuring that test reports, JUnit XML output, JSON output, and terminal logs generated by Cellrift are handled in accordance with applicable data protection obligations
- Following the responsible-use guidance above when choosing test targets

**Synthetic test data recommendation**

The built-in Cellrift scenario library uses exclusively synthetic test data:

- E.164 phone numbers from the Ofcom test range (`+44 7700 900xxx`) — these numbers are reserved for fictional use and are never assigned to real subscribers
- SIP URIs using `.lab.local` and `.cellrift.local` domains — non-routable, fictional domains
- Hostnames using `.lab.local` — non-routable

When authoring your own scenarios, use synthetic identifiers. Never use real subscriber MSISDNs, IMSIs, or SIP identities in scenario YAML files that may be committed to source control or shared.

**Output masking**

Cellrift masks E.164-format phone numbers in test report output (terminal, JUnit XML, JSON error fields) by default, replacing them with `[REDACTED]`. This reduces the risk of accidentally logging real subscriber identities if a real number is inadvertently used as a test variable.

**Processor appointment**

This DPA template confirms that no processor appointment is required for Cellrift itself, as Cellrift acts neither as a processor nor as a sub-processor. If you integrate Cellrift with a hosted CI/CD platform (e.g. GitHub Actions, GitLab CI), the terms of that platform govern the processing of any data passing through their infrastructure.
