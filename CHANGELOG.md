# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0] - Unreleased

### Added

- **SIP engine** — UAC emulation with REGISTER, INVITE, BYE, OPTIONS support over UDP, TCP, and TLS. Dialog state machine tracks call lifecycle. 3GPP IMS extension headers: P-Visited-Network-ID, P-Access-Network-Info, P-Charging-Vector, Path (RFC 3455, RFC 3327).
- **SDP** — offer/answer in SIP INVITE and 200 OK bodies, codec capture, remote port extraction (RFC 4566).
- **Diameter codec (experimental)** — AVP codec (RFC 6733 base + RFC 4006 credit-control AVPs), message builder/parser for UAR/UAA and CCR/CCA, TCP and real SCTP transport (SCTP is used where the kernel provides it, with an observed fallback to TCP otherwise — see the SCTP entries below). **The RFC 6733 §5.3 capabilities exchange and §5.5 device watchdog are now implemented and verified against the in-repo strict mock HSS; interoperability with a third-party Diameter implementation is not yet demonstrated** — see the new Diameter handshake entry below and `docs/roadmap.md`.
- **Diameter handshake now implemented (RFC 6733 §5.3/§5.5/§5.6)** — the client performs a Capabilities-Exchange-Request/Answer automatically on the first Diameter step of a scenario (no new scenario syntax: `origin_host`/`origin_realm` from the scenario's protocol config, or a step's own `Origin-Host`/`Origin-Realm` fields as a fallback, are now used to build the CER). 3GPP applications (Cx) are advertised inside `Vendor-Specific-Application-Id` (AVP 260, Vendor-Id 10415); RFC 4006 Credit-Control is advertised as a bare `Auth-Application-Id`, never vendor-wrapped. A client-only peer state machine (Closed → Wait-I-CEA → Open) tracks the handshake; responder/election states from §5.6.4 are omitted as unreachable for a client that never listens. Inbound Device-Watchdog-Request is answered with a DWA (§5.5) even while an application request is outstanding. The Hop-by-Hop ID is validated on every received answer, discarding anything that does not correlate. After a successful CEA, a step whose application the peer never advertised fails immediately with a named error, before any request is sent. **This is proven against Cellrift's own in-repo strict mock HSS only** (`TestAdapter_FailsAgainstStrictPeer`, inverted from asserting failure to asserting success) — it demonstrates the handshake is spec-shaped and self-consistent, not that it interoperates with third-party Diameter software. Real-peer evidence (Open5GS) came later; see the interop entries below.
- **Scenario engine** — YAML-based scenario parser and validator. Sequential step execution with cross-protocol shared state, template variable resolution (`{{ var }}`), capture/assertion framework.
- **CLI** — `cellrift run`, `cellrift validate`, `cellrift list` commands. Flags: `--format`, `--output`, `--target-host`, `--var`, `--fail-fast`, `--verbose`, `--timeout`.
- **Reporters** — Terminal (coloured, TTY-aware), JUnit XML, JSON output formats.
- **Docker image** — Multi-stage Alpine-based build, under 50 MB, includes built-in scenarios.
- **Scenario library** — 15 built-in scenarios under `scenarios/`: VoLTE registration, register/deregister, basic call, basic call over TLS, call rejected, and the impairment, connection-fault, assert-liveness, loss/reorder and malformed-traffic worked examples for SIP; Diameter UAR/UAA, credit control (CCR/CCA), S6a AIR/ULR, Cx MAR/SAR and the malformed-traffic example. Eleven carry a MOCK-ONLY marker (see each file's header); `internal/scenario/library_test.go` pins the count.
- **Schema/validator drift guards** — the Go validator now checks per-protocol transports, and `TestSchema_TransportEnumsMatchValidator` fails if `docs/scenario.schema.json` and `internal/scenario/validator.go` disagree on the allowed set.
- **CI pipelines** — GitHub Actions and GitLab CI with build, test, vet, scenario validation, and Docker image build.
- **GitHub Actions composite action** — `.github/actions/run-scenarios` for running Cellrift in CI. Not yet published to the Marketplace; reference it by path.
- **Persistent connections for connection-oriented transports** — `common.Connector` (`Connect(addr string) error`) is implemented by `TCPTransport` and `TLSTransport`, which now hold one connection across many Send/Receive pairs instead of dialling per Send. The Diameter adapter gains `Adapter.Connect`, the hook the RFC 6733 §5.3 CER/CEA exchange will use. UDP deliberately does not implement `Connector`; SIP's dial-per-send behaviour is unchanged and its test suite passes unmodified.
- **Real-peer Diameter interop, partial** — vendor-scoped AVP encoding fix: 3GPP AVPs (e.g. `Public-Identity`) now carry the V bit and Vendor-Id 10415 per RFC 6733 §4.4 / TS 29.229, where a real peer previously answered `5001 DIAMETER_AVP_UNSUPPORTED` against a plain-M encoding. `Destination-Realm` (AVP 283) fix: now sent on every application request, derived from the peer's own CEA `Origin-Realm` (RFC 6733 §6.6), where a real peer previously answered `3001 DIAMETER_UNABLE_TO_DELIVER` without it. A new `diameter-interop` CI job (`.github/workflows/interop.yml`) stands up `gradiant/open5gs:2.8.0` with a `mongo:7.0` sidecar and drives `scenarios/diameter/uar_uaa.yaml` against it. The job's genuine result: CER/CEA reaches `STATE_OPEN` and both AVP fixes are confirmed correct on the real peer's own wire log, but the UAR/UAA application exchange itself is answered `Result-Code 5005 DIAMETER_MISSING_AVP` (a missing `Vendor-Specific-Application-Id` grouped AVP the Cx UAR needs), not `2001`. This is a handshake proof plus a newly-identified, not-yet-fixed application-level gap — not full interop; see `test/interop/EVIDENCE.md` for the captured bytes.
- **Real SCTP transport** — Diameter now dials genuine one-to-one `SOCK_STREAM` SCTP associations (RFC 6733 §2.1) via `github.com/ishidawataru/sctp` (`v0.0.0-20251114114122-19ddcbc6aae2`, Apache-2.0, zero transitive dependencies) where the platform provides them, detected at runtime rather than by build tags, so one binary covers Linux, macOS and Windows. This is the project's first new direct dependency since 0.1.0 opened and was added under the `allow-new-deps` clearance the dependency policy requires.
- **Observable TCP substitution** — when SCTP is unavailable the run emits one `WARN: sctp unavailable (...), using tcp` line per process and records the substitution in `RunResult.Warnings`, which the JSON (`warnings`), JUnit (`<property name="cellrift.warning">`) and terminal (yellow `WARN:` line) reporters all render. Previously the substitution was completely silent.
- **Diameter's `transport:` scenario field is now honoured** — `tcp` uses TCP directly with no SCTP attempt and no warning; `sctp` (or an unset value) attempts SCTP with fallback. It was previously read for SIP but ignored for Diameter, so both values behaved identically.
- **New tunable `CELLRIFT_SCTP_CONNECT_TIMEOUT_MS`** (default 5000 ms) bounding how long an outbound SCTP dial blocks the caller. This bounds the caller's wait and does not cancel the dial itself — the library exposes no handle to interrupt an in-flight connect.
- **macOS/Windows support** is verified by cross-compiling (`go build` and `go vet` for `darwin/arm64` and `windows/amd64`, in the new `cross-build` CI job) against the library's own non-Linux stub. `go test` execution on those platforms is **not verified** — this repository has no macOS or Windows runner.
- **Embedded Diameter AVP dictionary** — the roughly 20 hand-maintained AVP constants are gone, replaced by `internal/protocols/diameter/dictionary/*.yaml` (`go:embed`), covering RFC 6733 base (20 AVPs), RFC 4006 credit-control (folded into base), and the full 3GPP TS 29.272 S6a/S6d/S7a/S7d/S13/S13' set (Table 7.3.1/1, all 175 AVPs) plus an initial three Cx AVPs already in use before this dictionary existed (`Public-Identity`, `Server-Name`, and a mistranscribed third entry — see the full Cx transcription entry below for the correction) — 198 AVP definitions in total, each carrying its own name, code, data kind, mandatory/vendor flags, and (for Grouped AVPs) a member list. Vendor-scoping — which AVP needs the V bit and Vendor-Id 10415 on the wire — now comes from each AVP's own dictionary entry instead of a 3-entry hardcoded table that covered only three Cx codes; a whole-dictionary self-consistency test (`TestAVPDictionary_SelfConsistency`) proves every Grouped AVP's member list resolves to a real entry and every code is unique, across base, Cx and S6a together.
- **Unknown Diameter AVP names now error instead of vanishing.** A field name in a scenario's `fields` map that the dictionary does not recognise fails twice: at `cellrift validate` time, with a Levenshtein did-you-mean suggestion, and again inside `buildAVPsFromFields` at send time. Previously a typo like `Public-Identitty` was silently dropped from the outgoing request with no error at either point.
- **Full 3GPP TS 29.229 (Cx) AVP dictionary** — all 54 Cx AVPs in the 600–655 code range (Table 6.3.1) are now transcribed into `cx.yaml`, each with its own spec clause citation. This closes out two defects found in the three-entry seed the dictionary shipped with: code 613 was mislabeled `Authentication-Information` (Grouped), a name that does not exist anywhere in TS 29.229 — the table's real row for 613 is `SIP-Item-Number` (Unsigned32); and `Visited-Network-Identifier` (600) was assumed present in earlier documentation but was never actually in the file, and is now added. The `AVPCodeAuthInfo` Go identifier is renamed to `AVPCodeSIPAuthDataItem`, now correctly resolving the real Cx Grouped AVP `SIP-Auth-Data-Item` (612). Four S6a Grouped AVPs (`UTRAN-Vector`, `APN-Configuration`, `Specific-APN-Info`, `Active-APN`) that deliberately omitted Cx-sourced members before this change now reference `Confidentiality-Key`, `Integrity-Key` and `Visited-Network-Identifier` by name. The embedded dictionary now totals 249 AVP definitions (20 base + 54 Cx + 175 S6a). Codes 656–658 (`Allowed-WAF-WWSF-Identities`, `WebRTC-Authentication-Function-Name`, `WebRTC-Web-Server-Function-Name`) are real Rel-13 assignments in the same spec table, deliberately left outside this file's stated 600–655 range.
- **`action: wait` is now dispatched** — a step with `action: wait` and `duration_ms: N` pauses the run for N milliseconds. It requires no `protocol:` (waiting is neither a SIP nor a Diameter operation) and is handled by the engine, in both the main step loop and inside a `parallel` group's sub-steps. Previously the validator and JSON schema both accepted the action and nothing executed it: the step resolved to an empty protocol and failed with `no adapter registered for protocol ""`. A missing or non-positive `duration_ms` is now a validation error rather than a silent zero-length sleep.
- **Raw response bytes are capturable** — `capture:` and `assert:` accept the reserved path `response.__raw`, which yields the unparsed response bytes (`StepResult.RawResponse`, populated since the first release and read by nothing until now). This is the only observable output when a response cannot be parsed at all. The `__` prefix follows the same reserved-name convention as the engine's internal `__body_*` step fields. Assertions reach it through the same lookup as captures, so `assert: response.__raw != null` is supported; the expression grammar has only comparison operators, so length or substring assertions are not expressible.
- **Diameter command coverage — AIR/ULR (S6a) and MAR/SAR (Cx).** Six Diameter commands are now sendable — UAR, CCR, AIR, ULR, MAR, SAR — resolved through a table-driven `CommandRegistry` that replaced `resolveCommand`'s switch; adding a seventh command is one map entry, not a new case. AIR (Authentication-Information-Request) and ULR (Update-Location-Request) run on S6a (Application-Id 16777251, command codes 318 and 316, TS 29.272 §7.2); MAR (Multimedia-Auth-Request) and SAR (Server-Assignment-Request) run on Cx (Application-Id 16777216, command codes 303 and 301, TS 29.229 §6.1). The client's CER now advertises S6a inside `Vendor-Specific-Application-Id` alongside Cx, since AIR/ULR finally give S6a something to negotiate for. Two AVPs the new commands' ABNF requires were missing from the dictionary and have been added: `Auth-Session-State` (RFC 6733 §8.11, code 277) and `RAT-Type` (code 1032, defined by TS 29.212 and reused by TS 29.272 §7.3.13) — the embedded dictionary now totals 251 definitions. `Auth-Session-State` is auto-injected for AIR/ULR/MAR/SAR only; UAR and CCR's encoded AVP sets are unchanged, pinned by a dedicated regression test. Grouped AVPs (e.g. `Requested-EUTRAN-Authentication-Info`, `Terminal-Information`, `SIP-Auth-Data-Item`) are now authored as nested YAML maps under a step's `fields:`, flattened internally to dotted paths, and encoded with the V bit and the Vendor-Id from each AVP's own dictionary entry — proven end-to-end on the wire for MAR's `SIP-Auth-Data-Item`. Two new worked scenarios ship this coverage: `scenarios/diameter/s6a_air_ulr.yaml` and `scenarios/diameter/cx_mar_sar.yaml`. **What was not proven:** every one of these six commands is exercised against Cellrift's in-repo mock HSS only — no real-peer run has been made for AIR, ULR, MAR, or SAR. The pre-existing `5005 DIAMETER_MISSING_AVP` gap on Cx requests against a real Open5GS peer (Cx's ABNF marks `Vendor-Specific-Application-Id` mandatory inside the request body, which Cellrift emits at CER level only) is untouched by this work and remains open for both UAR and the new Cx commands MAR/SAR.
- **Network timing impairment (SIP and Diameter)** — a scenario step can now declare an `impair:` block with `latency_ms`, `jitter_ms`, and `delay_ms`. Latency and jitter are applied by a shared transport decorator (`internal/protocols/common/impair`) that both protocol adapters arm on every step; the injected receive-side delay is charged once per assembled message, not once per socket read (a Diameter answer split across several TCP reads pays it once), and is clamped to the caller's own remaining timeout so an impaired step can never outlast the timeout it declared. `delay_ms` is applied by the adapter after a complete response has been parsed, deliberately unbounded, to exercise the peer's own timeout and retry behaviour. Each step reports how much of its duration was self-inflicted as `response.impair_delay_ms`, readable from `capture:`/`assert:` and rendered by all three reporters. `impair:` is valid on `action: send` only — `cellrift validate` rejects it elsewhere rather than silently ignoring it. Loss, duplication, reordering, and connection-level faults are NOT part of this change. A new worked example, `scenarios/ims/register_impaired.yaml`, ships alongside the existing scenario library.
- **Message drop, duplication, and reordering (SIP and Diameter)** — the `impair:` block gains two new boolean keys, and a new container action joins `parallel`/`wait`:
  - `impair: { drop: true }` — the step's message is built in full (encoder, AVP dictionary, and for Diameter the handshake, all still run) and then deliberately never written. The step reports `Status: passed` with `response.dropped == true`, and the run continues past it. No new `StepStatus` value was introduced.
  - `impair: { duplicate: true }` — the same already-built bytes are written to the wire twice, followed by one normal receive cycle. The step reports `response.duplicated == true`. A boolean, not a count. Only the first write pays any declared `latency_ms`/`jitter_ms`, a consequence of the transport decorator's one-shot arming design, pinned by test on both protocols. SIP additionally closes a response-attribution hole Diameter never had: since SIP performs no request/response correlation, a duplicated request's stray second response would otherwise leak into the NEXT step's read. A new bounded `drainDuplicateEcho`, backed by the new `CELLRIFT_SIP_DUPLICATE_DRAIN_MS` tunable (default 100ms), discards it before the step returns — mutation-tested by temporarily disabling the drain and confirming the leak reproduces.
  - `action: reorder` — a container step whose `send` sub-steps each declare `send_order: N`, with an optional group-level `timeout_ms`. Every sub-step's message is built before any of them is written, the writes happen in ascending `send_order` from the one goroutine that already owns the adapter's Send/Receive path — no background goroutine, no second reader — and results are returned in DECLARATION order regardless of wire order. An explicit, non-vacuous concurrency counter (`TestReorder_SingleGoroutineEverCallsReceive`, both protocols) proves only one goroutine ever calls the underlying transport's `Receive` during a reorder group. `drop`/`duplicate` may be composed on an individual reorder sub-step (e.g. "message 2 arrives before message 1, and message 1 is a duplicate"), proven by dedicated tests on both protocols.
  - A new Diameter session method, `session.receiveAnswers`, correlates a SET of Hop-by-Hop IDs in one blocking wait, closing a real pre-existing defect: the single-ID `receiveAnswer` permanently discarded any answer that did not match the ID it was currently waiting for, so a reordered Diameter group reading through it would have silently lost a response whenever wire order differed from declaration order.
  - **The disclosed limitation, stated plainly and not softened:** SIP performs no request/response correlation anywhere in this codebase — neither for reorder groups nor for ordinary sends. SIP's reorder support is therefore POSITIONAL: responses are read in the exact order requests were written and attributed by that position, trusting the peer to answer in receipt order. That trust holds against Cellrift's own synchronous, single-goroutine mocks and against typical UAS behaviour, but it is NOT equivalent to the Diameter implementation's Hop-by-Hop-ID correlation, which matches every answer to its own request regardless of arrival order. A peer answering out of receipt order would be mis-attributed silently under SIP's reorder support. Building real Call-ID/CSeq correlation for SIP is a larger change affecting every SIP step, not just reordering, and is not part of this release.
  - **What was not proven:** every capability here — drop, duplicate, and reorder, on both protocols — is exercised against Cellrift's in-repo mock peers only. No real-peer run was made for any of the three. The pre-existing `5005 DIAMETER_MISSING_AVP` gap against a real Open5GS peer is untouched.
  - The new `CELLRIFT_SIP_DUPLICATE_DRAIN_MS` tunable (default 100ms) bounds how long a `duplicate: true` SIP step spends discarding the peer's response to the second copy.
  - A new worked example, `scenarios/ims/register_loss_reorder.yaml`, demonstrates all three capabilities in one SIP-only scenario: a dropped REGISTER, a duplicated REGISTER, a reordered pair sent in reverse of their declared order, then a normal REGISTER — proven end-to-end through the real `cellrift run` code path by `TestRunScenario_LossReorderSurvivesProductionWiring`, which asserts against the mock peer's own arrival history (`sip.MockUASServer.ReceivedRequests()`) rather than step results alone.
- **Connection-level faults (SIP and Diameter)** — the `impair:` block gains four new keys, each reporting which fault fired via `response.connection_state`:
  - `impair: { reset: true }` — after the step's own `Send` succeeds, performs a real hard reset of the connection (`SO_LINGER 0` then close, so a genuine TCP RST reaches the peer) before any response is read. Reports `response.connection_state == "reset"`.
  - `impair: { truncate: true }` — writes only the first few bytes of the already-encoded message, too few to frame or parse, instead of the whole thing. Reports `response.connection_state == "truncated"`.
  - `impair: { abrupt_close: true }` — after `Send` succeeds, closes the connection with no clean shutdown (a plain FIN, not an RST) before any response is read. Reports `response.connection_state == "closed"`.
  - `impair: { sctp_abort: true }` — after `Send` succeeds, writes a real RFC 4960 ABORT chunk (`SCTPWrite` with `SCTP_ABORT` set) on the step's SCTP association, distinct from the graceful SHUTDOWN a bare close produces. Reports `response.connection_state == "aborted"`. `cellrift validate` rejects `sctp_abort` outright on any step that will not run over SCTP.
  - Every one of the four performs a REAL local socket operation — never a synthetic error: `SO_LINGER 0` then close for `reset`, a plain close for `abrupt_close`, a genuine RFC 4960 ABORT chunk for `sctp_abort`, a deliberate short write (a new internal constant, 8 bytes — shorter than the shortest well-formed frame either protocol can produce) for `truncate`.
  - A faulted step reports `Status: failed`, unlike a dropped step, which passes: a dropped step's impairment did exactly what was declared with no response ever expected, while a faulted step genuinely sent a message and then destroyed its own means of hearing the answer.
  - The fault-injecting code clears its own connection bookkeeping directly (`ConnFaultInjector`'s own transport-level state) rather than relying on `isDeadConnErr`'s error classification, because a closed SCTP association's next I/O returns a raw `syscall.EBADF` that the existing classifier does not, and never will, recognise — no change was made to `isDeadConnErr` itself.
  - **The Diameter reconnection fix:** `ensureConnected` gated re-handshaking solely on peer state and never consulted the connection's own torn-down state, so a step running after a self-inflicted fault would previously have failed on a connection the earlier step had already destroyed — a failure misattributed to a later, entirely innocent step. The fault-injecting code now resets peer state too, mutation-tested by temporarily removing the fix and confirming the two-step recovery test fails exactly as predicted. A related desync was found and fixed in the same series of changes: `AbortConn`'s connection teardown runs unconditionally even when the underlying SCTP_ABORT write itself errors, so the peer-state reset is now gated on a new `common.ErrConnFaultNotAttempted` sentinel (true refusal — nothing touched) rather than on a bare `err == nil` check, which had missed exactly that case.
  - **The SIP scope disclosure, stated plainly:** SIP performs no cross-step connection reuse — this client dials a fresh connection on every send — so its connection faults are scoped to each step's own dial-send-receive cycle and are NOT mid-session faults in the sense Diameter's are, where the one association the handshake established is held and reused across steps. Proven, not just asserted: `TestAdapter_ConnFault_ScopedToTheSameStep` confirms two SIP steps against one mock produce two separately accepted TCP connections, with the second passing cleanly and no reconnection logic anywhere in the SIP adapter — because none is needed.
  - **What is NOT part of this change:** the `timed_out` assertion key and the "assert liveness after fault" worked example, and malformed messages and cross-protocol frame injection (both later changes); and peer-INITIATED resets (a real `ECONNRESET` observed passively, as opposed to the self-inflicted faults above), which remain unclassified by `isDeadConnErr` and are a separate, not-yet-scoped concern.
  - A new worked example, `scenarios/ims/register_conn_fault.yaml`, demonstrates all three connection-oriented faults (`sctp_abort` is SIP-inapplicable and proven separately, entirely within `internal/protocols/diameter`'s own package tests) plus a recovering normal step. Running it deliberately exits non-zero: three of its four steps destroy their own connection by design. Proven end-to-end through the real `cellrift run` code path by `TestRunScenario_ConnectionFaultsSurviveProductionWiring`, which asserts against the mock peer's own pre-parse read history (`sip.TCPMockUASServer.RawReads()`) rather than step results alone.
- **`response.timed_out` — the assert-liveness-after-fault pattern (SIP and Diameter).**
  - `response.timed_out` is a new well-known response field, present on every `send` step for both SIP and Diameter, `true` only when the peer never answered within that step's own `timeout_ms`. Readable from `capture:` and `assert:` like `response.dropped`, `response.duplicated`, and `response.connection_state`. Mutually exclusive with `connection_state` by construction: a connection fault fires before any receive is attempted, so a faulted step reports `connection_state` and `timed_out == false`. Classification uses `errors.Is(err, os.ErrDeadlineExceeded)` (plus Diameter's own answer-timeout sentinel, `errAnswerTimeout`), never a `net.Error.Timeout()` type assertion.
  - A genuine SCTP receive timeout is now classifiable as a timeout as well as connection loss — `readFromSCTP`'s timeout error now wraps both `os.ErrDeadlineExceeded` and `net.ErrClosed` in the same value, so the existing reconnect-forcing behaviour over SCTP is unchanged.
  - `scenarios/ims/register_assert_liveness.yaml` — a runnable worked example of the assert-liveness-after-fault pattern on both protocols: a `reset` fault on a Diameter UAR followed by an ordinary UAR that only passes if the peer accepted a fresh association and re-ran RFC 6733 §5.3 CER/CEA, and the same pattern on a SIP REGISTER. Proven end-to-end through the real `cellrift run` code path by `TestRunScenario_AssertLivenessAfterFault` (the documented recovery outcome) and `TestRunScenario_TimedOutSurvivesProductionWiring` (`timed_out == true` against a peer that accepts a request and then stays silent, the true case the worked example itself cannot demonstrate against a healthy peer).
  - **The wire-visible-not-host-level caveat, stated in full:** a passing liveness step proves the peer is answering on the wire — it accepted a new connection, completed the protocol's own handshake where one exists, and produced a well-formed answer. It does NOT prove the peer's host is healthy, that no process crashed and restarted underneath, or that any internal subsystem survived. Cellrift is a client with no privileged access to the system under test; wire-visible liveness is the honest answer it can give.
  - Fixed a pre-existing defect surfaced by writing this change's production-path test: `responseFieldsMap` (Diameter) nested every AVP under a single `"avp"` map key only, so every built-in Diameter scenario's documented capture/assert convention (`response.Result-Code`, `response.Server-Name`, `response.CC-Request-Type`) silently resolved to `nil` — the engine's dotted-path lookup does a single-level walk with no fallback into a nested sub-map. Every AVP is now stamped at its own top-level key as well as inside the existing `"avp"` map, so both forms work.
- **Malformed messages and cross-protocol injection (SIP and Diameter).** A step can now declare a `malform:` block, structurally parallel to `impair:`, and a new `action: raw` bypasses the protocol encoder entirely:
  - `malform: { avp_length: { name: Session-Id, value: 9999 } }` — after `BuildRequest` produces a correctly-encoded Diameter message, the named AVP's own 3-byte Length field (and only that field) is overwritten with the declared value. Every other byte, including that same AVP's Code/Flags/VendorID/Data and every other AVP, is byte-identical to what the real encoder produced.
  - `malform: { msg_length: 9999 }` — the same post-encode override applied to the Diameter message header's own 3-byte Message Length field, independent of `avp_length` and composable with it on the same step.
  - `malform: { sip_header: { name: Via, op: missing|duplicate|overwrite, value: ... } }` — after `Serialise` produces a correctly-built SIP message, the named header line is deleted (`missing`), a second copy is appended immediately after the first (`duplicate` — deliberately adversarial, since real UAs are inconsistently first-wins or last-wins on a repeated header), or replaced in place with an arbitrary value (`overwrite`, `value` required). `duplicate`'s second line is invisible to a re-parse: `ParseMessage` coalesces two same-named headers into one comma-joined value, so every assertion about a duplicated header must read the raw wire bytes, never a re-parsed message — proven by a dedicated test on both the pure function and the live adapter path.
  - `malform:` is valid on `action: send` only, one level deep inside a `parallel` sub-step; `cellrift validate` rejects it anywhere else. Corruption is always applied to bytes the real encoder already produced — `EncodeAVP`, `BuildMessage`, and `Serialise` gained no corruption branch of their own, so nothing except the declared field ever diverges from correct encoding.
  - `action: raw` sends literal bytes directly over a step's own transport (`Transport.Send`), with no encoder, no request-builder, and no response parsing — `response.__raw`/`Response` are never populated for a raw step's own receive side. Two byte sources: `raw: { hex: "..." }`, a literal hex string decoded once by the engine, or `raw: { ref: "{{ a_prior_step.capture_name }}" }`, referencing an earlier step's own `response.__raw` capture. Both flow through the existing `state.Resolve` template machinery; a captured `[]byte` survives the round trip with no UTF-8 validation or byte loss. Reports `response.raw_bytes_sent`, the number of bytes actually written. A raw step reuses its protocol's existing connection where one is already open (for Diameter, handshaking first if no earlier step did); it never attempts to correlate or parse whatever the peer sends back.
  - Landed as validator support, engine dispatch, and BOTH adapters' implementation in one change — not split across a "validates but doesn't dispatch" boundary the way `action: wait` originally was. A dedicated dispatch-audit test requires `action: raw` to be dispatched by both the SIP and the Diameter adapter, distinct from the general dispatch audit's OR-across-sites rule (which exists so `assert_state`'s deliberately SIP-only dispatch stays valid).
  - **Adversarial scenarios are mock-only, stated plainly and enforced with no opt-out:** any scenario file declaring `malform:` or `action: raw` MUST carry the MOCK-ONLY marker. `scripts/check-scenario-labels.sh`'s guard was rewritten from a hardcoded enumerated file list into a content scan (`grep -rlE` for `malform:`/`action: raw` across the whole scenario corpus), so a scenario file written after this change ships is caught automatically, not only files known when the guard was written. Malformed and cross-protocol payloads are a different risk class from a delayed or dropped packet — sending either at a real, unconsented peer is deliberately adversarial traffic, not a timing fault.
  - **What was not proven:** no real peer — no real P-CSCF, no real HSS — has ever been sent malformed or cross-protocol traffic. - **SIP digest authentication (401 and 407)** — a SIP `send` that is answered `401` or `407` is now re-sent once, inside the same step, with a computed digest, so the step's own result is the final response. The retry increments the CSeq and carries a fresh `Via` branch; `WWW-Authenticate` is answered with `Authorization` and `Proxy-Authenticate` with `Proxy-Authorization`. MD5 and SHA-256 are supported with `qop=auth`, `nc` and `cnonce`, and when a peer offers several challenges the topmost supported one is used, echoing that challenge's own `opaque` (RFC 8760 section 2.4). The digest function is checked against the RFC 7616 section 3.9.1 and RFC 2617 section 3.5 vectors and two REGISTER values computed with `openssl`, before any peer was involved. Credentials come from three layers, most explicit first: `protocols.sip.username` and `password` in the scenario (a literal or a `{{ }}` template), then a `credentials_file`, then the ambient `CELLRIFT_SIP_PASSWORD` (the username has no ambient layer); a layer that is present but broken fails the step rather than falling through. `CELLRIFT_SIP_PASSWORD` is not `CELLRIFT_VAR_SIP_PASSWORD`: the latter only fills a `{{ sip_password }}` template. Every send result carries `response.auth.*` (`challenged`, `retried`, `algorithm`, `realm`, `nonce`, `qop`, `opaque`, `challenge_header`, `challenge_status`) for assertions. A resolved password and the credential header are removed from terminal, JSON and JUnit output, including under `--no-mask`; a credentials-file decode error that quoted the file's content was found and scrubbed. The interop rig gained three Asterisk endpoints that require digest (MD5 only, SHA-256 only, both offered), the scenario `register_digest_auth.yaml`, and two refusal gates, one that checks the container's own view of its auth wiring at boot and one that refuses unless the peer's own log shows it sent a 401. **Caveats that belong with the entry:** the pinned Asterisk validates the digest ARITHMETIC and not the header's grammar (it returned 200 for an unpadded `nc`, a quoted `qop`, the other challenge's `opaque` and a `uri` differing from the request line), so a pass against it is a proof of the arithmetic only; the grammar is pinned by in-process tests, `internal/protocols/sip/digest_test.go` and `auth_test.go`. `-sess` variants, SHA-512-256, `auth-int` and AKAv1-MD5 are not supported, and a challenge using only those is not answered. There is exactly one retry and no `stale` handling. `reorder` members and `parallel` sub-steps are not authenticated, by design. The authenticated TLS leg has not been run. The scenario has been run against the real peer locally only; no CI run of it is recorded yet. See `test/interop/EVIDENCE.md` run 13.

- **Prepared for publishing.** The README, roadmap, Asterisk guide, scenario library README and `docs/todo_next.md` now describe SIP as it is: answered by a real Asterisk in CI, with RFC 7616 digest authentication; they had still said SIP had no authentication and no peer in CI. The roadmap also wrongly said TLS skips certificate verification unless a CA is configured; verification is on by default against the system root pool. `s6a_air_ulr.yaml` and `cx_mar_sar.yaml` lose their `MOCK-ONLY` marker and join Guard C, because the `diameter-interop` job has been running both against the real Open5GS HSS and failing the build if they break. Comments that cited gitignored planning documents now carry their reasoning inline, machine-specific paths in the evidence files are shown as `<scratch>`, and a full-history `gitleaks` scan is clean. Commit hashes in `docs/pre-publication-audit.md` and `test/interop/EVIDENCE.md` come from the pre-publication history, which was squashed at publication; both files now say so.
- **Documentation truth pass, after an adversarial review found the front page contradicting itself.** The Status table said Diameter was "Experimental — all six commands proven against real peers" (a self-contradiction in one line) while thirty lines below, Features said "none of the six commands' application exchanges are proven against a real peer yet" — a stale sentence that survived every earlier sweep. The same table marked SIP **Ready to use** and Diameter **Experimental**, which is backwards: Diameter has two third-party peers answering in CI on every push, SIP has none and cannot answer an authentication challenge. Features also advertised SIP "UAC/UAS emulation" when no server mode exists, and "add to any CI runner with one `curl`" when no release or image is published. `docs/getting_started_asterisk.md` told readers to add an `Authorization` header "using credentials captured from a prior 401 step" — an instruction the binary cannot carry out, since it computes no digest. All corrected; SIP and SDP are now labelled Experimental with the authentication gap stated in the table itself, and the Asterisk guide gained an "Authentication is not implemented" section explaining what to do instead.
- **`MOCK-ONLY` is described accurately as a lint, not a safety control.** It constrains this repository's own scenarios and fails the build; it does not inspect scenarios you write, and nothing in the binary can tell whether a target is yours. The README previously implied a product-level guard.
- **`SECURITY.md` gained an upstream-disclosure path.** Cellrift ships deliberate malformation, so it will occasionally break third-party software; that is a vulnerability in that implementation and not ours to disclose, but the policy now says how to route it and asks that public issues not carry working reproducers for unpatched software.
- **The README's front-page scenario is now a real, validated scenario**, checked by `TestREADME_FirstScenarioExampleValidates` through the same path `cellrift validate` uses. The first draft of that block was itself invalid — missing `version:`, referencing an undeclared variable — which is exactly the rot the test now prevents.
- **`docs/todo_before_publishing.md` is now `docs/pre-publication-audit.md`.** It carried its own instruction to delete it before publishing, on the reasoning that a known-bugs list reads oddly in a public repo. That reasoning no longer applies with all 26 findings closed, so it is kept and reframed as what it is: a record of what this project found when it went looking for its own defects.

- **A SIP step now fails on any non-2xx final response**, with the status code and reason phrase in its error, even with no `assert:` block. It previously passed unconditionally, so a peer answering `500 Server Internal Error` produced a green step and exit 0 — a false pass for any scenario without an explicit `response.status_code` assertion. This mirrors Diameter, which has always failed on any `Result-Code` other than 2001; the two adapters now agree about what a protocol-level failure is. A 3xx fails too, deliberately, matching Diameter's strictness.
- **SIP's receive loop uses one absolute deadline per step.** It previously handed the full timeout to every read afresh, once per provisional response, so a peer trickling `180 Ringing` could hold a step for `CELLRIFT_SIP_MAX_PROVISIONAL × timeout` (25 minutes at a 30 s timeout) — and when the provisional budget ran out it reported the last 1xx as a *passing* final response. Both exits now fail with `response.timed_out == true`, which is what the tunable's documentation always claimed.
- **Assertions run on every step that declares them, passed or failed.** They were previously skipped on any step the adapter had already failed, so an assertion on a connection-fault step was dead code — including all three in `scenarios/ims/register_conn_fault.yaml`. An assertion can add a failure (appended to the protocol's own error, which is preserved) but cannot turn a failed step green. Negative testing — declaring that a step is *supposed* to receive an error — remains an open design item; see README "How a step passes or fails".
- **An assertion operand that does not exist is now an error**, not a vacuous pass. `missing_field != 503` compared the string `<nil>` against `503` and passed; a typo'd field name or a capture that found nothing produced a permanently green assertion. `== null` / `!= null` remain the way to assert absence or presence.
- **Assertion right-hand sides may be quoted.** `== "reset"` and `== reset` are now equivalent; in YAML a plain scalar's quotes are literal characters, so the quoted form previously never matched.
- **Scenario parsing is strict.** An unknown key at any nesting level is a parse error naming the line and key. `assertions:` (a typo of `assert:`) previously validated clean and ran the step with no checks. `docs/scenario.schema.json` already declared `additionalProperties: false`; the Go parser now agrees.
- **A step using a protocol with no `protocols:` entry fails validation**, with a message naming the block to add. It previously validated clean and failed at run time with `no adapter for protocol "sip"`.
- **`parallel` sub-steps must use distinct protocols.** Concurrent sub-steps on one protocol share a single adapter with no locking and would race on the session buffer and steal each other's answers; the shape is now a validate-time error until per-sub-step adapters exist.
- **TLS verifies the server certificate by default.** `transport: tls` with no cert block previously set `InsecureSkipVerify` silently. Verification is now on — against `ca_file` if given, otherwise the system root pool — and is disabled only by the new explicit `insecure_skip_verify: true` protocol key, which adds a warning to the run report. **This is a breaking change** for any scenario that relied on the silent default; `scenarios/ims/basic_call_tls.yaml` now opts in explicitly. `docs/cli-reference.md` and `docs/scenario.schema.json` are corrected — the schema's own `ca_file` description had documented the insecure default.
- **Per-step `timeout_ms` is honoured on the send path of both protocols.** Only SIP's `assert_state` read it before; SIP and Diameter sends waited the adapter default regardless.
- **The SIP dialog tracker accepts repeated and re-ordered provisional responses.** It rejected a second provisional of the same class (`ringing → ringing`) and thereby failed the canonical VoLTE flow `100 Trying → 183 Session Progress → 180 Ringing → 200 OK` at the 183, on a perfectly healthy call.
- **`validate` confirms each valid file** as `<path>: OK` instead of exiting 0 in silence.
- **`replay` is hidden and exits 2.** It is not implemented; it previously printed "not yet implemented" and exited 0, so a CI step invoking it succeeded while doing nothing.
- **An unknown flag on any subcommand now prints an error** before exiting 1; it previously exited in silence.
- **Terminal output** prints one `Error:` line per failed step (assertion failures were printed twice) and always shows a step's duration, including `0ms`.

### Fixed

- **SIP challenge parsing tolerates whitespace around `=`** (RFC 3261 section 25.1). A `WWW-Authenticate` or `Proxy-Authenticate` written `Digest realm = "r", nonce = "n", qop = "auth"` was split into four bogus challenges, losing the nonce and qop, so the failure named the wrong cause (`qop=(absent)` when qop was offered). The pinned Asterisk emits no spaces, so this was latent; the form is now parsed with the quote-aware splitting and per-challenge `opaque` unchanged. A test now also pins that the production cnonce generator yields a fresh 16-hex value per call (RFC 7616 section 3.4).

- **An SCTP read timeout no longer reads as a connection-state fault.** It rendered as `sctp read: timed out after 50ms: use of closed network connection: i/o timeout`, so a plain peer-silence timeout looked as though the association had already died, and this repository's own evidence file misdiagnosed it that way as a "last error wins" masking bug that does not exist. It now renders as `sctp read: timed out after 50ms: no data from peer (association then closed by this client)`. **The wrapping deliberately did not change**: `errors.Is(err, net.ErrClosed)` and `errors.Is(err, os.ErrDeadlineExceeded)` both still hold, directly and through a caller's `fmt.Errorf` wrap, because the first forces a reconnect and the second classifies the step as timed out; `TestReadFromSCTP_TimeoutWrapsBothSentinels` passes unmodified. The new error type has no `Timeout()` method, so the value itself is not a `net.Error` and a caller's `err.(net.Error)` retry check does not fire. That is the whole claim: the error still unwraps `os.ErrDeadlineExceeded`, so an `errors.As` consumer still reaches a value with `Timeout()`, exactly as it did before. The two historical quotations of the old text in `docs/todo_next.md` and `test/interop/EVIDENCE.md` are left as recorded corrections.
- **Every shipped scenario now uses the 3GPP test network (MCC 001 / MNC 01), and the policy script enforces it.** Nine scenarios carried UK PLMN identifiers: `ims.mnc001.mcc234.3gppnetwork.org` in five (`sctp_abort.yaml`, `register_basic.yaml`, `register_deregister.yaml`, `register_parallel_wait.yaml`, `loopback.yaml`) and `utran-cell-id-3gpp=234010001000001` in three more (`basic_call.yaml`, `basic_call_tls.yaml`, `call_rejected.yaml`), plus one SIP codec test fixture. MCC 234 is the United Kingdom, so `mnc001.mcc234` reads as a real operator's IMS domain rather than an obviously-synthetic one. The MSISDNs were always inside Ofcom's reserved range, which is precisely why `check-synthetic-data.sh` never noticed — it pattern-matched phone numbers only. It now checks MCC and `utran-cell-id-3gpp` too, skipping comment lines so a scenario can still explain in prose why it must not use a real MCC. The cell-id check found three of the nine files on its first run, and both new checks were mutation-tested. The Cx scenarios (`uar_uaa.yaml`, `cx_mar_sar.yaml`) were already correct — they had to be, because the HSS's provisioned IMSI implies MCC 001 and a mismatched IMPU makes the follow-up MAR fail `5002` (`test/interop/EVIDENCE.md`, run 6). Historical references in `EVIDENCE.md` are deliberately left as they are: they record what past runs actually sent, and rewriting them would falsify the record.
- **The darwin and windows builds compile again.** The `SO_LINGER`-based SCTP abort fix used `SCTPConn.SyscallConn`, which `github.com/ishidawataru/sctp` declares only in its `//go:build linux && !386` file; every other target gets a stub type without that method, so `GOOS=darwin go build ./...` and `GOOS=windows go build ./...` both failed to compile (windows additionally on `syscall.SetsockoptLinger`'s `syscall.Handle` parameter). `armSCTPAbort` is now split into `sctp_abort_linux.go` and `sctp_abort_unsupported.go`, with build tags that mirror the vendored library's own exactly — a plain `linux` tag would still have broken `linux/386`, which that library also serves from its unsupported file. The unsupported half returns an error rather than nil, so a future refactor that somehow reaches it reports a refusal instead of silently claiming an association was aborted. Verified by building and vetting `linux/amd64`, `linux/386`, `darwin/amd64`, `darwin/arm64` and `windows/amd64`. **This had been broken on `main` for eight days**, because the interop campaign that introduced it was reading the interop jobs and not the Non-Linux Build job — the same shape of gap as an assertion nobody checks. Also corrected two comment defects in the same file: `AbortConn`'s doc comment had been orphaned above `armSCTPAbort`, leaving `AbortConn` undocumented, and it still claimed the `SCTP_ABORT` cmsg constant was in use when that approach had been abandoned for `SO_LINGER`.
- **Cx and S6a requests now carry `Vendor-Specific-Application-Id` (AVP 260) in the request body**, as TS 29.229 §6.1 and TS 29.272 §7.2 require. Cellrift sent it at CER level only, so a real Open5GS HSS answered every UAR with `5005 DIAMETER_MISSING_AVP`. The AVP is added in the one place all six commands funnel through, so UAR, MAR, SAR, AIR and ULR are covered by one change; Credit-Control is deliberately excluded (RFC 4006's CCR ABNF has no such field, and vendor-wrapping it would be its own interop bug). **Confirmed on the wire** by a second real-peer run: the HSS's own dump of the UAR it received shows AVP 260 with Vendor-Id 10415 and Auth-Application-Id 16777216, alongside the vendor-scoped `Public-Identity` and `Destination-Realm` that earlier runs fixed (`test/interop/EVIDENCE.md`, run 2).
- **A Diameter step no longer passes when the peer's only verdict is an `Experimental-Result`.** RFC 6733 §7.6/§7.7 let an application report results in its own namespace, and 3GPP's Cx uses it exclusively: a real Open5GS HSS answers a successful UAR with `Experimental-Result-Code 2001 DIAMETER_FIRST_REGISTRATION` and **no base `Result-Code` at all**. Cellrift read only `Result-Code`, found nothing, and reported the step passed — so the same peer answering `5001 DIAMETER_ERROR_USER_UNKNOWN` in that field produced a green step and exit 0. The verdict now prefers `Result-Code` and falls back to `Experimental-Result-Code`, judging by RFC 6733 §7.1.3's 2xxx success *class* so both namespaces' successes pass and everything else fails with the field it came from named in the error. Found by decoding what a real HSS actually sent (`test/interop/EVIDENCE.md`, run 4).
- **`Experimental-Result` (297) and `Experimental-Result-Code` (298) are in the dictionary, and a Grouped AVP's members are flattened into the response namespace.** The answer's only verdict previously decoded as an unnamed `AVP-297` whose contents no scenario could reach; `response.Experimental-Result-Code` now resolves like any other field, with no new assertion grammar. Flattening is one level deep, which is every Grouped AVP this client can receive today.
- **The mock HSS answers a UAR the way a real Cx peer does** — `Experimental-Result`, in both lenient and strict mode — instead of a base `Result-Code` no Cx HSS sends. The lenient/strict split is about the §5.3 handshake gate, not about what an application answer says, and two modes disagreeing over a UAA's verdict would mean no scenario file could be correct against both. `NewSCTPMockHSS` is now strict too, so every mock a shipped scenario runs against models the peer's rules. Seven scenarios' UAR assertions were updated to match; `scenarios/diameter/uar_uaa.yaml` also stops asserting `server_name != null`, because a real HSS returns Server-Capabilities on a first registration and no Server-Name at all — an assertion that could only ever pass against a mock.

It also **refuses any scenario carrying the `MOCK-ONLY SCENARIO` marker** unless `allow-mock-only: true` is passed: the old default, `scenarios/ims/*.yaml`, included `malformed_sip_headers.yaml`, which sends deliberately malformed and cross-protocol traffic that must never reach a peer you do not own, plus three scenarios that fail by design. The workflow and the README snippet now name two scenarios that can actually pass against a real SIP target, and the README's `on: [push, pull_request]` — which would have dialled a lab on every push — is a manual trigger.
- **CCR/CCA is proven against a real OCS, completing all six Diameter commands.** A second CI job boots [SigScale OCS](https://github.com/sigscale/ocs) (Apache-2.0, Erlang, serving Ro/Gy — Credit-Control Application-Id 4), provisions a subscriber with a balance through its TMF APIs, and runs `scenarios/diameter/credit_control.yaml` against it: both CCRs answered `Result-Code 2001`. Three defects the peer named in one answer had to be fixed first: **`Auth-Application-Id` (258) was never sent** — Credit-Control is a bare application and carries it where a vendor-scoped command carries `Vendor-Specific-Application-Id`, so it is now auto-injected by the mirror image of that function, and the pinned CCR AVP set asserts a command is one or the other and never both; **`Service-Context-Id` (461) was missing** from both the dictionary and the scenario; and **`Rating-Group` was sent at the top level**, where a real OCS answers `5001`, instead of inside `Multiple-Services-Credit-Control` (RFC 4006 §8.16) — also added to the dictionary. `credit_control.yaml` loses its `MOCK-ONLY` marker and moves to the guard that asserts the opposite. TCP only: the OCS is reached through a published container port, which carries no SCTP.
- **Each interop scenario connects under its own Origin-Host.** freeDiameter keeps one peer object per `Origin-Host`, and all three scenarios advertised `test.cellrift.local` while running as three sequential processes — so they contended for one object, and the peer routed each new association's answers to the entry it was reaping. CI lost a complete `Authentication-Information-Answer` with an E-UTRAN vector and an `Update-Location-Answer` with full `Subscription-Data`, both `Result-Code 2001`, neither delivered. S6a now connects as `s6a.cellrift.local` and Cx as `cx.cellrift.local`, which also models reality better: an MME and an I-CSCF are different Diameter nodes. Both transports pass with no settle and no retries.
- **The settle-and-retry mitigation was removed.** freeDiameter keeps one peer object per `Origin-Host`, and each scenario runs as its own process; in the window where the previous association is being reaped the peer accepts a new one and then discards that association's first answer (`DROPPED 'Unable to forward answer to deleted / closed peer'`). It cost CI an AIR whose answer the HSS had already computed, vectors and `2001` included. It was added on the theory that a brief reaping window was swallowing answers; the next CI run failed **both** attempts, which disproved that premise, and the real cause turned out to be the shared identity above. It is gone rather than kept as insurance: it never turned a red run green, and a bounded retry over a peer bug is exactly what converts a real failure into a passing build.
- **Five of six Diameter commands are now proven against the real peer**, over both transports: UAR/UAA, AIR/AIA, ULR/ULA, MAR/MAA and SAR/SAA. Two identity rules had to be learned from the peer itself, and both are now encoded in the scenarios: **S6a's `User-Name` carries the IMSI** (an MSISDN is answered `5001 DIAMETER_ERROR_USER_UNKNOWN`), while **Cx's is the bare MSISDN with an IMPU of `sip:<MSISDN>@ims.mnc<MNC>.mcc<MCC>.3gppnetwork.org`** derived from the IMSI's PLMN (anything else is `5002 DIAMETER_ERROR_IDENTITIES_DONT_MATCH`). Scenario order is load-bearing and documented in `run-scenario.sh`: a UAR registers the IMPI/IMPU pair a later MAR needs, and a SAR assigns an S-CSCF that makes the same UAR answer `2002 SUBSEQUENT_REGISTRATION` rather than `2001`. The mock HSS now accepts both identities, so no scenario has to diverge from what the real peer wants.
- **The SCTP ABORT never worked, and the test could not see it.** `AbortConn` sent the abort as `SCTPWrite(nil, &SndRcvInfo{Flags: SCTP_ABORT})`, whose cmsg path returns `EINVAL` — the library's own `Close()` hits the same wall and discards the error. Every run reported `connection fault (aborted) failed to arm: invalid argument`, and the test passed anyway because `FaultedResult` stamps `connection_state = aborted` whether the fault armed or not and the test asserted only that state. `sctp_abort` has claimed a working RFC 4960 ABORT since it shipped. It now arms `SO_LINGER{1,0}` and lets the close abort the association — what sctp(7) documents and what the TCP reset already did — and a real Open5GS peer confirms the chunk arrives (`fd_sctp_recvmeta: Connection reset by peer`, then `STATE_OPEN -> STATE_CLOSED`). The test asserts the error does not say "failed to arm"; reverting the fix fails it. **Still unproven:** the liveness step after an abort, where the answer on the fresh association never arrives and our read loop reports its last error instead of its first.
- **The interop job proves real SCTP, not just TCP.** It now runs a matrix over both transports against the same Open5GS peer, and the peer's own log names the transport it accepted (`CONNECTED TO 'test.cellrift.local' (SCTP,soc#8)`). Two config lines had been blocking it — the vendored `hss-freeDiameter.conf`'s global `No_SCTP;` and a per-peer `ConnectPeer = ... { No_TLS; No_SCTP; }`, the second easy to miss because the global setting alone is not enough. The SCTP leg **fails rather than passes if Cellrift substitutes TCP**: the substitution is a recorded warning in the run's own report, and grading it silently would report an SCTP proof that was a TCP run. GitHub's runners do support SCTP: both legs are green on `ubuntu-24.04` at the same commit, with no `modprobe` or privileged step, and the SCTP leg's transport assertion armed throughout. Still unproven: a deliberate RFC 4960 ABORT against a real peer, and SCTP on macOS/Windows.
- **The interop harness provisions an MSISDN.** `up.sh` provisions a subscriber by IMSI, and the vendored `open5gs-dbctl` has no command that can add an MSISDN — every `add*` path writes `"msisdn": []`. The HSS's Cx handler calls `ogs_dbi_msisdn_data()` before anything else, so every UAR failed with "Cannot get MSISDN-Data" no matter how correct the request was. It is now set directly and verified, failing the harness loudly rather than surfacing later as an apparent interop defect.
- **Every application request now carries `Origin-Host` (264) and `Origin-Realm` (296).** RFC 6733 §6.3 and §6.4 require both in every Diameter message; Cellrift put them in the CER only, and a real Open5GS HSS answered UAR `5005 DIAMETER_MISSING_AVP` naming `Origin-Host` once the Session-Id fix below let the request get that far. The identity injected is the one the handshake resolved, so a request and its CER always agree about who the client is. A step that declares either AVP keeps its own value. The adapter's DWA already did this correctly — only application requests did not.
- **The UAR now carries `Auth-Session-State` (277).** TS 29.229 §6.1.1 marks it mandatory, but the command registry excluded UAR from the injection deliberately, because adding an AVP would change bytes a regression test pinned exactly. The pin was pinning a defect: it has been updated, and the test asserting "UAR must NOT get Auth-Session-State injected" now asserts the opposite. CCR still does not get it — RFC 4006 §3.1 does not require it there.
- **`scenarios/diameter/uar_uaa.yaml` declares `Visited-Network-Identifier`**, the last AVP the Cx UAR's ABNF marks mandatory. It is the roaming network the subscriber attaches from — scenario data, not something Cellrift can invent the way it can a Session-Id.
- **The strict mock rejects a request missing `Session-Id`, `Origin-Host` or `Origin-Realm`** with 5005, table-driven. Three CI round trips against a real HSS were spent discovering those three omissions one at a time, because the mock accepted every one of them; it now models the base protocol's universal rules, not only the handshake.
- **Every application request now carries a `Session-Id` (AVP 263), as its first AVP.** Cellrift sent none at all, on any command. RFC 6733 §8.8 makes it mandatory and requires it immediately after the header, and so does every ABNF this client can send — Cx, S6a and Credit-Control. It is why a real Open5GS HSS still answered `5005 DIAMETER_MISSING_AVP` after the AVP-260 fix above ("the number of occurences (0) is < the rule min (1) for 'Session-Id'"), and it left the peer unable to build a well-formed answer either: its UAA had no `Session-Id` to echo, so it failed its own parse rules and closed the connection. A declared `Session-Id` is never replaced, only hoisted to the front — CCR-I, CCR-U and CCR-T belong to one session and must share one identifier across three steps. Generated ids follow §8.8's recommended `<DiameterIdentity>;<high 32>;<low 32>;<optional>` form and are unique per step. **What was not proven:** fixed in code and pinned by tests across all six commands; the interop job has not been re-run since, so this is fixed by construction, not yet by evidence.
- **The strict mock HSS now rejects an application request with no `Session-Id`** with `5005 DIAMETER_MISSING_AVP`, as a real freeDiameter peer does. It previously echoed whatever it found — including nothing — and answered `2001`, which is exactly how a mandatory AVP's total absence stayed invisible behind a green suite. A mock more forgiving than any real peer proves nothing, so strict mode now models the peer's message rules, not only its handshake.
- **Four adapter tests raced the mock peer's own read goroutine** and failed on the first CI run while `make test` had been green throughout. A step that deliberately does not wait for an answer — a connection reset, an abrupt close, a truncated send, an SCTP abort, a duplicate's second copy — returns as soon as its bytes are written, so nothing ordered the peer's read against the assertion that followed it. A 16-core developer machine schedules the mock's goroutine within microseconds and the assertion always passed; a 2-core runner does not. The mocks gained `WaitForRequestsOfCommand`, `WaitForRequests` and `WaitForRawRead` accessors (exported, on the exported mocks) that wait for the observation with a bounded timeout instead of assuming it, and the SIP tests' hand-rolled `require.Eventually` waits now use them too. `make test` and CI run a second, single-threaded pass (`GOMAXPROCS=1`) that turns this class of race from an occasional CI failure into a deterministic local one — it reproduces all four every time.
- **The PII masker leaked the second of two phone numbers separated by a single character** (`+447700900001,+447700900002` → `[REDACTED-1],+447700900002`) in terminal, JSON and JUnit output alike. The regex's consuming trailing-context group swallowed the separator; the boundary is now checked without consuming it.
- **`cellrift assert` printed the actual compared value unmasked**, putting a live MSISDN from the input file into CI logs. It now masks its output like the run reporters.
- **`diameter.MockHSS.Close()` could hang forever** when the client had not closed its side first, and panicked on a second call. It now closes every accepted connection before waiting and is idempotent. (Exported mock; downstream users of it were affected.)
- Minor leaks: a file descriptor per TCP silence-fault connection in the SIP mock, and one timer per physical SCTP read.

### Removed

- **`validate --strict`** — declared, documented, and never read. Strictness is now unconditional, so a flag promising it would only imply its absence meant something looser.
- **The unimplemented `receive` action** — `action: receive` was accepted by the validator and listed in `docs/scenario.schema.json` since the initial commit but was dispatched nowhere and used by no scenario. `send` already performs a synchronous send-then-await-response on both protocols. A new test now fails the build if any action in the validator's allow-list lacks a dispatch path, so this class of dead surface cannot reappear silently.

### Requirements

- **Go 1.26.11 or later.** The `go` directive in `go.mod` is pinned to 1.26.11 because earlier 1.26.x patches carry `crypto/tls`, `crypto/x509`, `net/http` and `net/textproto` advisories that `govulncheck` flags as reachable from the TLS transport. CI derives its toolchain from `go.mod` via `go-version-file` so the two cannot drift.

### Known limitations

- **One of Diameter's six commands has no real-peer interop evidence: CCR.** The `diameter-interop` CI job drives five of them against a genuine `gradiant/open5gs:2.8.0` HSS on every push, over both TCP and real SCTP — CER/CEA to `STATE_OPEN`, Cx UAR/UAA answered `Experimental-Result-Code 2001`, S6a AIR/ULR answered `Result-Code 2001`, and Cx MAR/SAR answered (`test/interop/EVIDENCE.md`, runs 1–9). CCR is untested because **this harness runs no Credit-Control peer**: the image ships no OCS and its `open5gs-pcrfd` speaks Gx (16777238) rather than Credit-Control (4), so Cellrift's post-CEA gate correctly refuses to send into it. Open-source OCS implementations do exist and an earlier version of this file wrongly said they did not, generalising one Docker image into the whole ecosystem; `docs/todo_next.md` item 3 names candidates and the work. Two AVPs RFC 4006 §3.1 marks mandatory in the CCR — `Auth-Application-Id` and `Service-Context-Id` — are still not sent, which is reasoning from the spec with no peer yet to confirm it. Do not read five proven commands as an interoperable Diameter stack.
- **No outbound device-watchdog timer.** Cellrift answers an inbound DWR (§5.5), but does not itself send DWR on an idle connection (RFC 3539's Tw) — deferred, not required for correctness within a short scenario run.
- **Diameter's RAR/RAA (re-authorization) is not implemented.** UAR, CCR, AIR, ULR, MAR, and SAR now cover S6a and Cx; RAR is the one command not implemented.
- **SCTP connect timeout bounds the wait, not the dial.** A dial exceeding `CELLRIFT_SCTP_CONNECT_TIMEOUT_MS` returns to the caller on time, but its dial goroutine stays parked until the kernel gives up — the library exposes no way to cancel an in-flight connect.
- **SCTP is Linux-only, by the library's construction.** `ishidawataru/sctp` ships a `sctp_unsupported.go` for every non-Linux target (and for `linux/386`) whose every entry point returns `ErrUnsupported`, so `transport: sctp` on macOS or Windows always falls back to TCP with the `transport: requested sctp, used tcp (sctp unavailable: ...)` warning. Those platforms are verified by cross-compilation (`go build`, `go vet`) only — the right amount of verification for a path that is a stub. Earlier entries in this file describing macOS/Windows SCTP as merely "untested" were misleading and are corrected here.
- **SIP is UAC-only in scenarios.** The UAS side exists as an in-process mock for the test suite, not as a runnable server mode.
- **SIP still has no automated real-peer interop test.** Diameter now has one: `diameter-interop` (`.github/workflows/interop.yml`) stands up a real `gradiant/open5gs:2.8.0` HSS in CI and proves the CER/CEA handshake (and, per manual verification, DWR/DWA) against it — but its coverage stops at the handshake; the application-level exchange is not yet proven there. SIP has been verified by hand against Asterisk 18+ only; no CI job stands up a third-party SIP implementation.
